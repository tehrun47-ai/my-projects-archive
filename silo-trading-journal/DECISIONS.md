# SILO — تصمیم‌های مهم و چرایی‌شون

## هسته‌ی ژورنال همیشه رایگانه
هیچ‌وقت، تحت هیچ شرایطی، ثبت و بستن معامله نباید نیاز به فعال‌سازی یا پرداخت داشته باشه. زیرساخت Premium/فعال‌سازی برای آینده نگه داشته شده، ولی به هسته‌ی محصول وصل نیست.

## بدون Rewrite کردن Migration‌های قدیمی
هر تغییر دیتابیس، یه فایل Migration جدید و شماره‌دار می‌گیره (مثلاً `0026_security_hardening.sql`)، هیچ‌وقت یه Migration قدیمی که قبلاً روی یه محیط واقعی اجرا شده، ویرایش نمی‌شه. این‌جوری تاریخچه‌ی دیتابیس همیشه قابل‌ردیابی و امن می‌مونه.

## Session معاملاتی، روز، و بازه‌ی زمانی هیچ‌وقت از کاربر پرسیده نمی‌شه
همه‌ی این‌ها از روی زمان ثبت خودِ معامله محاسبه می‌شن — نه چیزی که کاربر دستی وارد کنه. این باعث می‌شه داده همیشه دقیق و قابل‌اتکا باشه، و کاربر هم مجبور نباشه فیلد اضافه پر کنه.

## هیچ رتبه‌بندی‌ای بدون حداقل نمونه‌ی ۵
مثلاً «بهترین ستاپ تو» هیچ‌وقت با ۲-۳ تا معامله اعلام نمی‌شه — این می‌تونه گمراه‌کننده باشه. این قانون هم توی خودِ دیتابیس (سطح View) اجرا می‌شه، نه فقط توی رابط کاربری.

## ماشین‌حساب ریسک باید دقیق باشه، نه تقریبی
وقتی یه نماد (مثل جفت‌ارزهای ین ژاپن) فرمول محاسبه‌ش پیچیده‌تره، راه‌حل درست، پیاده‌کردن فرمول واقعیه — نه فقط گذاشتن یه هشدار «تقریبیه». فقط جاهایی که واقعاً امکان محاسبه‌ی دقیق بدون مشخصات کارگزار وجود نداره، باید صریح «تقریبی» علامت بخوره.

## هر تغییر دیتابیس، فقط دقیقاً همون تغییر رو انجام بده
وقتی یه Migration امنیتی می‌نویسیم (مثل Issue #2)، نباید هیچ منطق تجاری یا رفتار محصول رو تغییر بده — فقط دقیقاً همون چیزی که خواسته شده (مثلاً `search_path` یا دسترسی‌ها). این باعث می‌شه Reviewer بتونه سریع و مطمئن تأیید کنه.

## معماری Navigation: نوار پایین موبایل، Sidebar دسکتاپ
Responsive بودن یعنی تغییر واقعی ساختار، نه فقط عریض‌ترشدن ستون‌ها. موبایل نوار پایین داره (خانه/تاریخچه/ثبت معامله/تحلیل‌ها)، دسکتاپ همون ۴ مقصد رو توی یه Sidebar کناری نشون می‌ده.

## توکن‌های رنگ (Theme Tokens) باید در سطح پایه تعریف بشن، نه توی یه حالت خاص
یه اشتباه واقعی که پیش اومد: یه‌سری توکن رنگ که قرار بود مستقل از تم باشن (مثلاً رنگ متن روی عکس)، اشتباهی فقط توی بلوک تم تاریک تعریف شده بودن — یعنی توی تم روشن اصلاً وجود نداشتن. درس: هر Token که باید در همه‌ی تم‌ها یکسان باشه، باید توی بلوک پایه (`:root`) تعریف بشه، نه توی یه بلوک تم خاص.

## Workflow نهایی: همه‌چیز از طریق GitHub Issue/PR
استاد Issue می‌سازه با جزئیات دقیق کار → Claude از `main` یه Branch جدا می‌سازه → فقط همون کار رو انجام می‌ده → تست کامل → PR باز می‌کنه → **متوقف می‌شه**. Merge و تصمیم نهایی همیشه دست استاده. Claude هیچ‌وقت مستقیم روی `main` کار نمی‌کنه یا خودش Merge نمی‌کنه.
